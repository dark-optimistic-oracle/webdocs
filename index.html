Dark Optimistic Oracle

A privacy-preserving optimistic oracle that resolves disputed off-chain assertions using Aleo private records and publicly verifiable aggregate state.

Current scope

The deployed interface targets the core assertion, dispute, vote, and settlement program. Governance and cross-chain components are future integrations.

Protocol

Lifecycle

  1. Assert

    An asserter publishes an ID, title field, content hash, economic terms, and dispute and voting deadlines.

  2. Dispute

    A disputer challenges before the dispute deadline by posting the matching public DOOR amount.

  3. Vote

    A token holder spends a private DOOR record to create a voting right, then confirms or denies the assertion.

  4. Settle

    The program evaluates the public aggregate tally after the deadline and enforces eligible awards or refunds.

Data visibility

Privacy model

Dark Optimistic Oracle uses a hybrid design. Applications need public assertion state and an observable result, while voters benefit from private ownership and reward records.

Public

  • Assertion metadata and content hash
  • Deadlines and stake parameters
  • Asserter and disputer addresses
  • Aggregate confirm and deny counters
  • Program code and finalization rules

Private records

  • Voting rights
  • Vote receipts
  • Voter token inputs and change
  • Voter awards and unused-right refunds
Visibility boundary

Private Aleo records do not imply that every piece of transaction metadata is hidden. Integrators should reason from the deployed program and Aleo network semantics rather than treating “private voting” as a blanket anonymity claim.

System design

Architecture

Browser
  ├─ Provable API → program availability, height, public mappings
  └─ Shield wallet → authorization and transaction submission

              dark_optimistic_oracle.aleo
                         │
                         ▼

The browser creates Aleo transaction requests and the wallet authorizes them. The oracle program records public state and invokes the canonical token registry for DOOR operations. Aleo proves private transition inputs without placing their plaintext record contents in public mappings.

Web app

Interface capabilities

  • Look up public assertion state by a known assertion ID.
  • Create an assertion after hashing claim text locally.
  • Challenge an assertion before its deadline.
  • Create a private voting right and submit confirm or deny transactions.
  • Submit settlement, private award, and refund transactions.

Aleo mappings are key-value stores and do not expose a complete assertion index. Applications should preserve assertion IDs or provide an external index. The web app does not upload or store the original claim text; only its derived field is submitted, so the source text and encoding must be retained elsewhere.

Network

Aleo testnet

The public interface expects:

  • dark_optimistic_oracle.aleo deployed from the core repository.
  • The canonical testnet token_registry.aleo.
  • Shield connected to Aleo testnet.

The app checks the oracle program and current height through the official Provable API. Transaction controls remain disabled when testnet or the program cannot be verified. The token-registry workaround repository is for local devnet use only.

Future integrations

Roadmap boundaries

The broader project design includes governance that can use the oracle for decisions, bridge adapters that make results available on other networks, and remote contracts that consume those results. These components require separate design, security review, and deployment work and are not presented as current product capabilities.
